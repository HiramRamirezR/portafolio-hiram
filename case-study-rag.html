// RAG · LangChain · ChromaDB · Ollama

Private document Q&A with a local RAG pipeline

How I built an offline Retrieval-Augmented Generation API — and the decisions that make it production-shaped.

View Code All projects

Overview

Ollama RAG is a Python backend that lets a user upload PDF documents and ask questions in natural language. Instead of answering from the model's parametric memory, the system retrieves the most relevant fragments from the document and constrains the answer to them. Everything runs locally: the LLM, the vector store and the documents never leave the machine.

The problem

Teams accumulate knowledge in PDFs — SOPs, reports, contracts — that general chatbots cannot safely answer from: either the data is not allowed to leave the company, or the model invents details. I wanted a repeatable pattern: a small API that answers questions only from the supplied documents, running on a laptop and deployable on a server without vendor lock-in.

Goals

  • Ground every answer in retrieved document context — no free-form generation.
  • Run fully local: no API keys, no per-token billing, private by default.
  • Expose it as a clean REST API so any frontend, script or agent can call it.
  • Keep the pipeline modular: swapping chunking, embeddings or the LLM must be a small change, not a rewrite.

Architecture

Two paths meet at the vector store: an ingestion path that turns documents into searchable chunks, and a query path that turns a question into a grounded answer.

Ingestion: documents are loaded with PyPDF, split into overlapping chunks, embedded into vectors and upserted into ChromaDB.

Query: the question runs a similarity search for the top-k chunks, those chunks are injected into the prompt as context, and the LLM answers from that evidence — not from its parametric memory.

Key decisions

Chunking with overlap

Fixed-size chunks with overlap keep semantic units intact across boundaries: too small loses meaning, too large dilutes relevance and burns context window.

Retrieve, then ground

Top-k chunks go into the prompt and the model is told to answer only from that context — if the context does not contain the answer, it must say so instead of guessing.

Local model via Ollama

Privacy first: documents and prompts stay on the machine, there is no per-token cost, and the same code runs offline. The model can be swapped without touching the pipeline.

Thin vector-store layer

ChromaDB is embedded and zero-config for document-scale corpora. The interface stays thin so it can be replaced by pgvector when the app moves next to a production Postgres.

Results

  • Runs end-to-end offline: no API keys, no per-token spend, no data egress.
  • One REST surface (upload + ask) powers a chat UI, a script or an agent tool call.
  • The pipeline became the reference architecture I reuse for client RAG systems.

Next steps

  • Retrieval evaluation: RAGAS-style faithfulness and answer-relevance checks over a golden set of question → context pairs, so changes to chunking cannot silently regress quality.
  • Hybrid search + reranker: combine BM25 with vector search to catch exact terms (names, codes, part numbers) that embeddings blur.
  • Streaming: SSE responses to cut time-to-first-token and make the chat experience feel immediate.
  • pgvector + semantic caching: keep embeddings next to production Postgres and reuse answers for repeated questions to cut latency and cost.
